# 숨은 박

> 들리는 박에 맞춰 탭한다. 박 소리는 점점 사라지고, 무음 속에서도 박을 맞추면 콤보와 배율이 오른다.
> 시험하는 것은 **내적 템포** — 시각 반응이 아니라 예측이다.

한 판 30초. 탭 또는 스페이스 하나로 한다. 미스로 죽지 않는다.

플레이: https://eastar80.github.io/game04/

## 규칙

박은 **4박 단위 마디**로 흐른다.

- **소리 마디** — 클릭음이 나고 원이 펄스한다. 항상 4박.
- **무음 마디** — 소리도 펄스도 없다. 박은 그대로 흐르고 있다. 여기서 맞히면 배율이 붙는다.

무음 박을 맞힐 때마다 그 박의 배율이 1, 2, 3… 으로 올라간다.
무음 마디가 얼마나 긴지는 **현재 콤보**가 정한다.

| 콤보 | 무음 박 수 | 최대 배율 |
|------|-----------|-----------|
| 0–3 | 2 | ×2 |
| 4–7 | 4 | ×4 |
| 8–15 | 6 | ×6 |
| 16+ | 8 | ×8 |

소리 마디는 늘 4박이므로, 콤보가 오를수록 한 판에서 소리 마디가 차지하는 비율이 줄고
총점 상한이 급격히 올라간다. **이것이 위험-보상 축이다**(원칙 8).
그리고 한 번의 MISS 가 콤보를 0으로 되돌려 무음을 2박까지 끌어내린다.

### 판정

| 판정 | 오차 | 효과 |
|------|------|------|
| PERFECT | ±40ms | 3점 × 배율, 콤보 +1 |
| GOOD | ±90ms | 1점 × 배율, 콤보 +1 |
| MISS (놓침) | 박 뒤 90ms까지 입력 없음 | 콤보 0, "놓쳤어요" |
| MISS (빗나감) | 판정 창 밖 입력 | 콤보 0, "너무 빨라요 / 느려요 ±NNNms" |

- 소리 박의 배율은 항상 ×1. 점수 = Σ(판정 점수 × 배율).
- MISS 가 나면 무음이 즉시 끝나고 **다음 박부터 소리 마디로 복귀**한다. 구조가 리셋된다.
- 한 박에 인정되는 입력은 하나. 두 번째 입력은 빗나감으로 처리한다
  (이 경우 이미 판정된 박이 대상이므로 다음 박을 죽이지는 않는다 — 콤보만 끊긴다).
- 다가올 박을 향해 크게 헛스윙하면 그 박이 날아간다(빗나감).

> 결과 화면에 **최고 배율**을 따로 두지 않는다. 무음 k번째 박을 맞히려면 1~k-1 을 모두
> 맞혀야 하므로 배율은 **최장 무음 성공과 항상 같은 값**이다(봇 320판으로 확인).
> 한 줄을 더 쓸 정보가 없어 `4박 ×4` 처럼 한 칸에 함께 적는다.

## 화면

- **가운데 큰 원** — 소리 박마다 확장→수축. 무음 구간엔 어둡게 굳고 펄스가 없다.
- **원 아래 점** — 남은 무음 박 수. 움직이지 않는다(시각 카운팅 도우미가 되면 안 된다).
- **탭할 때** — 판정 텍스트와 `-23ms` 형태의 오차. 빠름은 파랑, 느림은 빨강, 정확히 0은 금색. 0.4초 후 페이드.
- **상단** — 점수 · 최고 · 콤보 · 배율 · 남은 시간 바. 최고 점수를 넘는 순간 금색 연출과 상승음.

## 수치와 이유

모든 수치는 `index.html` 의 `DIFFS` 표 한 곳에 있다. 튜닝은 그 표만 고친다.

| 값 | 기본 | 이유 |
|------|------|------|
| `bpm` | 100 | 박 간격 0.6초. 걷는 속도에 가까워 몸으로 유지하기 쉽다 |
| `duration` | 30초 | 60 → 45 → 30. 플레이해보며 두 번 내렸다. 원칙 5(30초~2분)의 하한 |
| `perfect` | ±40ms | 콤보를 계속 쌓으려면 집중이 필요한 폭 |
| `good` | ±90ms | 이 시각이 곧 "놓침" 확정 시각이다. 창을 두 개로 나누지 않는다 |
| `countIn` | 4박 | 첫 소리 마디 4박이 곧 튜토리얼(원칙 3) |
| `soundBeats` | 4 | 소리 마디를 고정해야 무음 비율 증가가 그대로 보상이 된다 |
| `scorePerfect/Good` | 3 / 1 | 3배 차이. GOOD 만으로도 판은 굴러가지만 기록은 PERFECT 가 만든다 |

**입력 오프셋** 슬라이더 하나(−100 ~ +100ms, 저장됨)만 둔다. 그 외 캘리브레이션은 없다.
탭이 실제보다 늦게 잡히면 음수로, 빠르게 잡히면 양수로 맞춘다.

| 3 한 입력 한 스킬 | 탭 하나. 시험하는 능력은 내적 템포 하나. 첫 소리 마디 4박이 설명을 대신한다 |

| 7 주스 | 무음 PERFECT 시 흔들림 강도·상승음 피치·파편 수가 배율에 비례. `prefers-reduced-motion` 존중 |
| 8 위험-보상 | 무음이 길수록 배율이 커지고, 한 번의 MISS 가 그 전부를 되돌린다 |
| 9 시스템 하나 | 코어 루프만. 리더보드는 직접 플레이로 재미를 확인한 뒤에 붙였다 |

## 리더보드

**`전체 랭킹` 과 `내 기록` 두 가지를 본다.** 게임이 끝나면 결과 화면에서 바로 열린다.

### 내 기록 (로컬, 전체 저장)

**끝난 판은 전부 남는다** — 상위 몇 개만이 아니라 전부다. 판마다 점수·최대 콤보·PERFECT
비율·최장 무음·평균 오차·날짜를 함께 저장하므로, 점수뿐 아니라 **늘고 있는지**가 보인다.
맨 위에 `N판 · 최고 · 평균` 요약이 붙고 최고 기록 줄이 강조된다. 보관 한도는 500판.

저장은 어댑터를 통한다: `window.storage`(아티팩트 환경, 비동기) → `localStorage` → 메모리.
stacker 와 같은 형태다.

### 전체 랭킹 (Supabase)

Supabase REST 를 `fetch` 로 직접 부른다. **JS 클라이언트 라이브러리는 쓰지 않는다** —
"외부 라이브러리 없음" 컨벤션을 지키기 위해서다. 코드에 박힌 키는 공개용(publishable)이라
HTML 에 그대로 들어가도 된다. 실제 방어는 서버의 RLS 정책과 `CHECK` 제약이 한다.

플레이어는 저장소의 익명 ID(`beat.playerId`)로 구분한다. 로그인은 없다.
등록은 **수동**이다 — 이름을 넣고 `등록` 을 눌러야 올라간다.

**네트워크가 죽어도 게임은 그대로다.** 6초 안에 응답이 없거나 실패하면 안내로 떨어지고
`내 기록` 은 그대로 보인다. 제출 실패도 게임을 막지 않으며, 로컬 기록은 이미 저장돼 있다.

> **전체 랭킹은 배포판(GitHub Pages)에서만 동작한다.** Claude 아티팩트로 띄운 미리보기는
> CSP 가 외부 `fetch`/XHR 을 전부 막기 때문에 랭킹이 항상 "불러오지 못했습니다" 로 뜬다.
> Supabase 설정 문제가 아니다 — 주소창에 REST URL 을 직접 넣으면 정상 응답이 온다.
> 미리보기에서도 `내 기록`(로컬)은 전부 정상이다.

플레이 중 좌측 상단에 **바로 위 순위와 그 점수**가 뜬다(`3위 412`). 리더보드는 게임이
끝나야 보이므로, 넘어야 할 숫자는 플레이 중 화면에 따로 있어야 하기 때문이다(원칙 6).

> 부정 점수는 원리적으로 막을 수 없다 — 게임이 전부 브라우저에서 돌기 때문이다. 지금은
> 서버의 `CHECK` 제약으로 말이 안 되는 값만 거른다. **점수에 영향을 주는 난수가 없어**
> 입력 기록만으로 재현되므로, 서버가 리플레이해 점수를 계산하는 방식이 가능하다.
> 그때는 서버 코드가 필요하다(Workers/Edge Function).

### 테이블 만들기

stacker 의 `scores` 테이블은 `stage` 제약이 stacker 단계 이름으로 묶여 있어 재사용할 수
없다. 같은 Supabase 프로젝트에 **새 테이블**을 만든다. SQL 편집기에서 한 번 실행한다:

```sql
create table public.beat_scores (
  id          bigint generated always as identity primary key,
  name        text   not null check (char_length(name) between 1 and 12),
  score       int    not null check (score >= 0 and score <= 1000),
  player_id   text   not null check (char_length(player_id) between 8 and 64),
  created_at  timestamptz not null default now()
);

alter table public.beat_scores enable row level security;
create policy "누구나 읽기"   on public.beat_scores for select using (true);
create policy "누구나 등록"   on public.beat_scores for insert with check (true);

create index beat_scores_rank on public.beat_scores (score desc, created_at asc);
```

`score` 상한 1000 의 근거: 30초 · 100bpm 에서 **이론 최대는 414점**이다
(모든 박을 PERFECT 로 치는 σ=0 봇으로 계산). 튜닝 여유를 두고 1000 으로 잡았다.
`duration` 을 올릴 때만 이 상한을 다시 봐야 한다 — 45초면 672, 60초면 933 이다.

## 자동 플레이 테스트

```bash
npm install && npm test
```

`window.__beat` 훅: `state`, `nextBeatTime`, `tap(atAudioTime)`, `reset()`, `replay(inputs)`,
`replayStepped(inputs, stepSec)`, `bot(sigmaMs, seed)`.
`reset()` 은 오디오 시계가 깬 뒤에 판이 시작되므로 Promise 를 돌려준다 — `await` 해야 한다.

오차 σ 가우시안으로 박을 노리는 봇 3종, 각 20판:

| σ | 점수 평균 | 최장 무음 성공 | PERFECT 비율 |
|------|-----------|---------------|--------------|
| 15ms | 413 | 8박 (20판 전부) | 100% |
| 50ms | 194 | 평균 6.0박 | 54% |
| 120ms | 58 | 최대 4박 | 22% |

확인되는 것:

- 점수가 σ 순으로 **단조 감소**한다 — 정확도가 곧 점수다.
- σ=15 봇은 무음 8박 배율에 **도달**하고, σ=120 봇은 무음 4박을 **못 넘는다**.
  요청서에서 예상한 대로 나왔다.
- 봇 입력 기록으로 `replay()` 를 다시 돌리면 점수가 **완전히 같다**(원칙 1 검증).
- 같은 입력을 30/60/120/240Hz 진행 간격으로 돌려도 결과가 **같다**(주사율 독립).
- **첫 판 회귀**: 늦게 깨는 `AudioContext` 를 주입해도 카운트인이 얼지 않고 박 간격이 0.6초로 균일하다.
- **기록**: 끝난 판이 전부 저장되고 새로고침해도 남는다. 랭킹 서버가 막혀도 게임과 내 기록은 멀쩡하다.

**이 수치는 밸런스 확인용이지 재미의 증거가 아니다.** 재미는 직접 10판 해보고 판단한다.

## 배포 (GitHub Pages)

`main` 에 푸시하면 `.github/workflows/pages.yml` 이 배포한다. 다만 **저장소에서 Pages 를
한 번은 손으로 켜야 한다** — `GITHUB_TOKEN` 으로는 사이트 생성이 되지 않는다
(`Create Pages site failed: Resource not accessible by integration`).

저장소 **Settings → Pages → Build and deployment → Source** 를 **GitHub Actions** 로.
그 뒤 `main` 에 푸시하거나 Actions 탭에서 `Deploy to GitHub Pages` 를 직접 실행하면 된다.

**전체 랭킹은 이 배포판에서만 동작한다** — 아티팩트 미리보기는 CSP 가 외부 요청을 막는다.
